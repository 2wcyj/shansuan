# 膳算联网手机版：自动保存与持续个性化方案

- 日期：2026-10-19。
- 状态：已确定“联网使用、自动保存用户信息、持续改进个性化、仅面向中国大陆、首版邀请10位朋友试用、初期每月运行预算100元以内、首轮使用手机网页”的方向；本文其余内容为下一版实施建议。
- 适用范围：首轮为中国大陆多用户手机网页版，安卓与iPhone安装包留待后续。
- 当前基线：原有 [PRD](../PRD.md) 和 [实际架构](architecture.md) 仍描述电脑本地版。本文不表示联网版已经实现，也不改写本地版验收结果。

## 1. 用户最终获得的体验

用户登录后填写一次基本档案，之后持续记录饮食、照片、饮水、睡眠、运动和感受。应用自动保存有效输入与执行结果；换手机后登录同一账号可以继续使用。

推荐前读取该用户的档案、近期实际记录和个人记忆。例如，用户反复反馈午饭准备时间不足，后续优先推荐更容易准备的午餐；明确表示某道菜不喜欢，后续减少推荐并提供替代。以上为说明场景，不是对当前使用者的资料判断。

每次调整说明依据、改了什么和主要营养估算变化。用户可以查看、纠正、停用或删除记忆，恢复调整前方案。历史实际记录保持原有事实。

## 2. 自动保存的准确含义

| 信息 | 保存方式 | 何时影响推荐或统计 |
| --- | --- | --- |
| 建档、资料编辑草稿 | 有效字段编辑后自动保存，显示保存状态 | 草稿不直接覆盖正式健康限制；确认后生效 |
| 身体资料、目标、疾病及过敏原 | 校验并确认后保存为新版本 | 新版本立即约束后续建议；旧计划标记待复查 |
| 实际餐食与分量 | 用户确认吃过后提交，防止重复记录 | 服务器保存成功后才计入摄入 |
| 照片识别 | 保存图片和识别草稿，保留用户修订 | 识别成功本身不代表已经进食 |
| 饮水、睡眠、运动与反馈 | 用户填写或点选后自动提交对应操作 | 成功保存后更新实际记录和后续调整依据 |
| 问答记录 | 在已告知的账号保存范围内保留对话与引用 | 仅取与当前问题相关的内容，不把猜测写成事实 |
| 系统归纳的偏好 | 保存为带来源和状态的个人记忆 | 按证据强弱使用，可随时纠正；健康事实须确认 |

页面区分“正在保存”“已保存”和“保存失败，待重试”。只有收到服务器确认才显示已保存。请求带操作唯一标识和数据版本，重复点击、自动重试不能重复记餐或叠加饮水；多设备同时编辑发生冲突时保留输入并展示差异。

短暂断网时保留当前输入，恢复后重试。原生手机端若提供可跨重启的待同步队列，必须加密并绑定账号，退出或换号时处理未同步内容；队列不能把上一账号的数据提交给下一账号。手机网页内测阶段先保留当前页面输入并提示连接状态，不承诺浏览器关闭后尚未提交的草稿必然恢复。健康资料不写入普通浏览器localStorage。

## 3. 怎样越来越了解每一位用户

个人上下文分为三部分：

1. **已确认档案**：身体信息、目标、健康限制、过敏原、饮食类型、预算和时间条件。用户确认的事实优先。
2. **真实历史**：实际餐食、完成情况、用户明确跳过/替换的原因、反馈和身体测量。没有记录不解释为没有进食，也不把一次波动解释为趋势。
3. **可管理的个人记忆**：常用备餐时间、喜欢的食材、实际能接受的食物形态及反复出现的执行困难。每条记忆附来源、时间、置信状态和是否正在使用。

初期用结构化查询、规则和摘要实现；建议读取近7天执行情况、近30天相关变化及仍有效的长期记忆。查询时间窗口不等于数据保留期限。暂不引入复杂的向量数据库或为每位用户训练独立模型。

明确表达的普通偏好可以即时形成记忆；从行为推断的偏好先标记为“系统推测”，达到足够证据后才提高权重。单次跳过可能是忙、买不到或已经吃了别的，不能直接推断为讨厌。重复证据门槛和有效期需作为可配置工程规则，并用真实试用反馈验证。

疾病、过敏、药物、孕期和医学结论不能从照片、聊天或行为自动确诊。疑似相关表述只形成待确认提醒；过敏与明确健康限制始终优先于口味和执行率。

“个人档案 → 关于我的记忆”提供：查看内容与依据、修改、删除、暂停个性化记忆。删除记忆后不能立即从旧摘要重新生成；需清理相关派生摘要并保留必要的排除标记。用户修改正式档案时，使冲突记忆和缓存失效。

## 4. 推荐与更新流程

```text
验证当前账号
  → 仅读取该账号的已确认档案、相关记录和有效记忆
  → 先检查急症表达与明确健康限制
  → 排除过敏风险及明显冲突候选
  → 按当前目标、偏好、预算、时间和多样性排序
  → AI理解问题、解释选择和组织回复
  → 程序核算有来源的营养估算，校验输出
  → 展示推荐、依据、替代与未知项
  → 用户确认实际执行并留下反馈
  → 更新个人记忆与未来未执行方案，保留调整差异和版本
```

模型每次使用最新个人上下文；这种个性化可以在不修改模型权重的情况下持续改进。所有账号仍使用受控发布的模型和规则版本。产品代码、模型或推荐规则的升级经过测试、小范围发布和可回退流程，不能因为一个用户的反馈就自动改变所有人的规则。

个人健康信息默认仅用于提供该用户的服务，不默认用于训练公共模型。模型服务的存储、训练和处理区域要求需要在选型时核实。运营分析应与个人原始健康资料分离。

## 5. 从当前项目演进的技术方案

| 部分 | 建议方向 |
| --- | --- |
| 手机界面 | 复用React与现有深浅主题，适配触摸、拍照、键盘、窄屏和网络状态；首轮手机网页内测，后续再评估用Capacitor制作安卓/iOS安装包 |
| 账号与权限 | 增加注册/登录、登录恢复、会话过期和设备退出；面向中国大陆，具体登录方式结合发布主体条件和首批试用范围确定 |
| 服务端 | 复用并拆分FastAPI营养与推荐服务；通过HTTPS访问，新增用户身份和逐资源授权 |
| 业务数据库 | 云端PostgreSQL及版本迁移，全部个人实体有所有者；查询和写入双向约束归属，可增加数据库行级隔离 |
| 照片 | 私有对象存储，访问需鉴权，短期授权链接；服务端核对归属，不能仅凭文件编号访问 |
| AI | 服务器调用受控模型服务，图片分析与问答用任务队列、重试和每用户额度；密钥不打包进手机端 |
| 记忆 | 结构化个人记忆、事件来源、用户纠正和失效规则；摘要只能由该用户有权限的数据生成 |
| 移动存储 | 手机安全存储保护令牌与必要加密缓存；Windows DPAPI文件方案不直接照搬到手机 |
| 运维 | 备份恢复、访问审计、用量成本、失败监控、模型/规则/应用版本管理；日志默认不记录健康正文、照片或完整对话 |

原有过敏过滤、营养核算、实际记录与计划分离、反馈调整、七天报告等业务规则应复用。单机进程锁、单人库、回环访问限制和串行队列需要为联网多用户重新设计，不能仅开放当前18765端口。

## 6. 主要数据与接口增量

| 数据 | 必要字段 |
| --- | --- |
| 用户、会话与隐私选择 | user_id、认证关联、设备会话、服务条款/隐私告知版本及同意时间、账号状态、时区 |
| 现有档案/餐食/计划/生活/反馈/报告/照片/问答 | user_id、原业务字段、version、created_at、updated_at；事件时间和用户本地业务日期分开 |
| 用户记忆 | id、user_id、类型、内容、确认/推测状态、来源事件、证据强度、创建/最后确认/失效时间、启用状态及版本 |
| 调整记录 | 用户、原方案版本、新方案版本、触发依据、营养估算差异、规则/模型版本、确认与撤销状态 |
| 同步操作 | 用户、操作唯一标识、实体版本、结果、重试状态；避免重复和冲突覆盖 |
| 数据处理任务 | 用户、任务类型、状态、创建/完成时间、失败码、取消/超时及删除传播结果 |

建议接口：登录/退出/恢复；`GET/PATCH /me/profile`；现有餐食/记录/反馈/计划/报告接口增加鉴权、版本和幂等保护；`GET/PATCH/DELETE /me/memories`；个人数据导出、账号删除和设备会话管理。

用户身份从服务端验证的会话取得，不信任请求正文里的user_id。管理员和食品合作模块不拥有修改用户健康事实或推荐安全规则的权限；首版不开发商家模块。

## 7. 隐私、恢复与本地资料迁移

- 注册和首次收集健康资料时明确说明用途、保存位置、模型处理与用户权利，只收集完成服务所需信息。
- 数据传输加密，数据库、照片和备份静态加密；密钥单独管理。导出和删除均验证当前身份。
- 上线前确定健康资料、原始照片、对话、日志和备份的保留期限；删除传播到记忆、摘要、缓存和派生数据，备份按明确期限清退，不能宣称备份已即时抹除。
- 云端恢复必须保留用户归属和删除记录，不能通过恢复旧备份重新暴露已删除账户的数据。
- 电脑已有资料不自动上传。后续提供“预览导入 → 选择目标账号 → 核对范围 → 确认上传 → 校验结果”的一次性迁移流程，导入幂等且有失败恢复。原有本地文件和备份按用户选择保留。

## 8. 连续实施顺序和完成标准

每一阶段增加并运行对应的有效测试，失败先修复；阶段通过后提交，再继续。上线使用真实密钥、发布应用、上传当前个人资料及发生费用前，另行执行具体配置和发布步骤。

| 阶段 | 交付 | 必须检查 |
| --- | --- | --- |
| 0. 明确上线范围 | 已确定中国大陆、手机网页、邀请10位朋友试用、每月运行预算100元以内；继续确定登录方式、AI使用频率、存储/模型服务选型及保留期限 | 依赖与费用可解释；现有本地版不受影响 |
| 1. 多用户基础 | 联网服务、登录、独立档案、私有照片存储、会话与备份 | 两个账号完整交叉访问/写入/下载/任务查询均被拒绝；过期会话不可使用 |
| 2. 核心闭环联网化 | 档案、计划、手动/照片记餐、问答、快捷反馈和七天报告 | 原有业务规则回归；弱网超时、重复请求、多设备冲突和跨时区日期正确 |
| 3. 自动保存和个人记忆 | 保存状态、草稿、个人上下文、记忆查看纠正、解释调整 | 重开/换机一致；错误不假成功；纠正后不使用旧记忆；删除后不从旧摘要复活；健康事实不自动猜测 |
| 4. 真机小范围试用 | 安卓与iPhone上的手机网页、触摸与相机权限体验；原生安装包留待后续 | 真机拍照、权限拒绝、键盘、前后台切换、登录恢复、弱网和账号切换均通过 |
| 5. 发布准备 | 隐私材料、适用市场要求、商店素材、监控、额度与可回退版本 | 全量测试、备份恢复演练、账号删除演练、费用上限及小范围发布验收通过 |

## 9. 评估是否确实更了解用户

用同一测试档案比较增加相关记录/反馈前后的推荐：执行困难应降低，理由引用真实证据；无关或缺失数据不应制造新结论。确认过敏原后，即使多次表示喜欢相关食物，也仍硬性排除。用户纠正偏好后下一次建议应生效；另一个账号的建议和记忆不得变化。

试用时观察推荐被接受/替换的原因、记录负担、记忆纠正率、重复推荐率、响应耗时、失败率及每用户AI成本。保留显式“不是这个原因”“暂时如此”“以后不要这样推荐”入口；不使用压力评分或无依据的健康改善承诺。

## 10. 中国大陆首发安排

用户已确认：只面向中国大陆使用者。首发使用简体中文，默认业务时区为Asia/Shanghai；现有食物库的来源和估算限制继续明确标注，不把国外基础库冒充完整中餐资料库。

建议使用中国大陆区域的应用服务、数据库、私有照片存储和备份，并选择大陆可稳定访问的AI服务。选型时核对实际处理区域、日志、训练用途和子服务，不能仅凭供应商名称推断数据处理位置。第一阶段保持单区域架构，控制复杂度与成本。

发布准备按中国大陆适用的域名/网站和APP备案、发布主体、健康信息隐私要求，以及各安卓商店和中国区App Store的具体要求逐项核实。具体手续、主体资格和费用在平台选型后确认，本文不将尚未核实的事项视为已经满足。

用户已确认先邀请10位朋友试用。按本人也使用计算，首批容量规划为11个独立账号；邀请名额与当前活跃会话数分别管理。先跑通账号、自动保存、个人记忆、拍照、反馈、换机恢复和数据删除，再根据结果决定扩大范围。

## 11. 邀请试用版的建议安排

1. **加入方式**：仅受邀账号可以进入，关闭公开注册。邀请码有有效期和使用次数限制，兑换后仍使用独立账号登录；邀请码不代替账号身份验证。
2. **独立资料**：每位朋友拥有自己的档案、照片、问答、记录与记忆。邀请管理者只能管理邀请资格和必要的用量信息，默认不能查看朋友的健康正文。
3. **试用闭环**：建档 → 生成计划 → 手动/照片记餐 → 简短反馈 → 调整下一日方案 → 七天回顾。记忆能查看、纠正和删除，结果有真实保存状态。
4. **反馈入口**：收集页面问题、推荐不方便的原因和记忆错误；用户选择是否附带截图或诊断信息，不默认附上健康记录和完整对话。
5. **费用控制**：设置每人AI调用额度、图片大小限制、任务排队与服务总预算告警。额度不足时明确说明，手动记录和已有资料仍可使用；不循环重试造成无上限费用。
6. **版本更新**：试用更新记录变更内容，验证历史资料兼容并保留恢复路径；出现影响数据的失败先停止扩大邀请，修复回归通过后继续。

邀请门槛、账号隔离、邀请过期/重复兑换、超额提示、反馈脱敏和旧版本数据升级均需对应有效测试。首轮通过手机浏览器内测；安卓安装包和iOS测试分发留待后续，届时核实分发条件与费用。

## 12. 每月100元以内的试用预算

用户已确认：初期每月运行费用上限为人民币100元，涵盖服务器、数据库、照片存储与备份、网络流量、AI及所选登录服务。具体服务尚未选购，当前没有已核实的供应商报价；不能据此承诺任何人数和调用量都能在100元内运行。

以下仅为采购预算分配上限，不是现行价格或购买承诺：

| 项目 | 月度预算上限 | 控制办法 |
| --- | --- | --- |
| 基础服务 | 50元 | 初期应用和PostgreSQL共用小型服务器，不自建GPU推理服务；实际资源是否足够由压测验证 |
| AI调用 | 25元 | 按需调用文字/视觉服务；限制图片尺寸、上下文、输出长度、重试次数与每人额度 |
| 照片、异地备份与额外流量 | 10元 | 私有存储、压缩上传、明确保留期限；备份不只保存在应用服务器同一磁盘 |
| 预留 | 15元 | 覆盖小幅用量变化和按月折算的必要固定费用 |
| 合计 | 100元 | 服务核价超过上限时先调整方案，不直接购买 |

首批按本人和10位朋友、共11个账号测算。用户已确认先使用手机网页，通过浏览器链接进入；支持条件允许时添加到主屏幕，具体提示按浏览器适配。验证核心闭环后再评估安卓/iPhone安装包。手机网页入口不会自动变成应用商店安装包；本轮不发生原生应用分发费用。

邀请制内测优先评估“邀请码加入 + 用户名/密码登录与安全恢复”，减少短信等额外服务成本；此为建议，尚未确认。每日计划、营养计算与基础统计沿用程序规则，只有需要理解问题或图片时调用AI；个人记忆用结构化资料与摘要实现，不为每人训练模型。

费用预警不等于硬性停止计费。实现需预留并发任务的最坏成本，调用前占用额度、完成后结算；达到上限停止新增付费AI任务，避免靠事后告警控制开销。同步设置供应商可用的余额/额度限制，禁用未授权自动充值。查询、手动记餐和导出不因AI额度用尽而停止。

采购时核对日常价格、续费价格、最低计费周期、流量和存储单价，不以首年促销或试用赠送额度证明长期可行。域名和其他必要年费按月折算计入运行总预算；开发者账号等年度/一次性发布费用另外列清，在确认总成本后再选择分发方式。

新增验收要求：核价表不超预算；并发、重试和任务失败不能绕过额度；费用耗尽时明确提示且保留手动功能；后续按试用真实用量复算，不把预算分配当成实际账单。

### 12.1 11个账号的用量测算方式

采购比较先使用统一测算场景，而非要求试用者预先知道精确用量。例如每人每天3次拍照、5次问答，按30天计算为990次照片分析与1650次问答；这是核价场景，不是已承诺额度或用户确认的使用频率。另计摘要更新、失败重试、视觉输入与输出长度，并用实际测试请求校验单次成本。11个账号的并发、各自额度与服务总额度都需测试。

计算固定服务费用、存储/流量、必要费用折算后，剩余预算才可分配给AI。上述场景若超出预算，先比较更合适的模型、上下文长度与试用额度，并明确告知；不通过省略账号隔离、备份或隐私保护降低成本。
